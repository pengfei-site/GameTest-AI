**项目名称：** GameTest AI  
**项目代号：** GTAI-001  
**设计阶段：** STEP 07 — 测试点人工审核与数据管理  
**文档版本：** V1.0  
**状态：** 核心设计规则已确认，待进入数据库实现阶段

---

## 一、设计目标

GameTest AI V0.1 的数据管理系统主要解决以下问题：

1.  管理不同游戏项目及其策划文档。
2.  保留策划文档的历史版本。
3.  保存每次 AI 需求分析的独立结果。
4.  保存每次 AI 测试点生成批次，不覆盖历史结果。
5.  区分 AI 原始测试点和人工修改后的测试点。
6.  支持逐条审核、批量审核、驳回、重新编辑。
7.  保留测试点完整操作历史。
8.  支持按生成批次查看、审核和导出测试点。
9.  提供 SQLite 数据库自动备份、手动备份和安全恢复能力。

核心设计原则：

*   历史数据可追溯。
*   AI 原始结果不可被人工修改覆盖。
*   人工审核拥有最终决定权。
*   不同生成批次之间相互独立。
*   重要数据操作必须保留历史记录。
*   删除操作优先采用逻辑删除。
*   数据恢复必须具备安全保护措施。

## 二、技术方案

| 项目 | 方案 |
| --- | --- |
| 数据库 | SQLite |
| 数据库操作 | Python |
| 数据格式 | JSON + SQLite |
| 内部唯一标识 | UUID |
| 时间记录 | 统一使用标准时间格式保存 |
| 数据备份 | SQLite 官方备份机制 |
| 操作历史 | 独立历史数据表 |
| Excel 导出 | openpyxl |

V0.1 暂不引入 MySQL、PostgreSQL 等服务端数据库，不建立多用户账号系统。

## 三、数据库核心表设计

数据库共设置 6 张核心表。

### 3.1 projects — 游戏项目管理表

用途：管理不同游戏项目。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 项目唯一 ID |
| name | 游戏项目名称 |
| description | 项目描述 |
| status | 项目状态：active / archived |
| created\_at | 创建时间 |
| updated\_at | 更新时间 |
| archived\_at | 归档时间 |

规则：

1.  创建项目时生成唯一 ID。
2.  项目默认状态为 active。
3.  项目删除操作改为归档。
4.  归档项目不允许创建新的需求分析和生成批次。
5.  归档项目的历史数据仍可查看。
6.  归档项目支持恢复。
7.  不执行项目物理删除。

### 3.2 documents — 策划文档管理表

用途：管理项目中的策划文档及其版本。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 文档版本唯一 ID |
| project\_id | 所属游戏项目 |
| document\_group\_id | 同一份策划文档的版本分组 ID |
| document\_name | 文档名称 |
| version | 文档版本 |
| file\_name | 原始文件名称 |
| file\_type | 文件类型 |
| file\_path | 原始文件存储路径 |
| parsed\_content | 文档解析文本 |
| is\_current | 是否为当前版本 |
| is\_deleted | 是否逻辑删除 |
| deleted\_at | 删除时间 |
| created\_at | 上传时间 |

规则：

1.  同一份策划文档支持多个版本。
2.  每个版本独立保存原始文件和解析文本。
3.  新版本上传后成为当前版本。
4.  旧版本不覆盖、不物理删除。
5.  每份文档通过 document\_group\_id 关联版本。
6.  文档删除采用逻辑删除。
7.  被历史需求分析或生成批次引用的文档版本必须保留。
8.  新版本上传不会改变历史批次关联的文档版本。

示例：

*   每日体力领取 V1
*   每日体力领取 V2
*   每日体力领取 V3

三个版本均独立保存。

### 3.3 requirement\_analyses — 结构化需求分析表

用途：保存 AI 对策划文档的结构化需求分析结果。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 需求分析唯一 ID |
| project\_id | 所属项目 |
| document\_id | 关联的具体文档版本 |
| module | 功能模块 |
| analysis\_content | 完整结构化需求 JSON |
| created\_at | 分析时间 |

analysis\_content 保存：

*   summary
*   business\_rules
*   preconditions
*   states
*   numeric\_constraints
*   exception\_cases
*   open\_questions

规则：

1.  每次需求分析创建一条新记录。
2.  需求分析必须关联确定版本的策划文档。
3.  已被生成批次引用的需求分析不可直接覆盖。
4.  重新分析必须创建新的需求分析记录。
5.  一个需求分析可以关联多个生成批次。
6.  被历史批次引用的需求分析禁止删除。

### 3.4 generation\_batches — 测试点生成批次表

用途：记录每次 AI 测试点生成任务。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 批次唯一 ID |
| project\_id | 所属项目 |
| requirement\_analysis\_id | 关联的需求分析记录 |
| batch\_number | 项目内批次编号 |
| total\_points | 生成测试点数量 |
| validation\_report | Python Validator 完整报告 |
| review\_report | AI Reviewer 完整报告 |
| final\_status | 最终生成状态 |
| created\_at | 批次生成时间 |

final\_status 包括：

*   ready\_for\_manual\_review
*   needs\_manual\_review
*   review\_failed
*   validation\_failed

规则：

1.  每次 AI 生成都创建独立批次。
2.  重新生成不覆盖历史批次。
3.  每个批次必须绑定一份确定版本的需求分析记录。
4.  保留所有历史批次。
5.  批次不允许物理删除。
6.  批次详情展示生成时间、关联需求分析、测试点数量、AI 审查结果和人工审核进度。

### 3.5 test\_points — 测试点数据表

用途：保存 AI 生成的测试点、人工修改内容及审核状态。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 测试点内部唯一 ID，UUID |
| batch\_id | 所属生成批次 |
| point\_id | AI 生成的业务编号 |
| original\_content | AI 最初生成的完整 JSON |
| current\_content | 当前使用的完整 JSON |
| ai\_review\_status | AI 审查状态 |
| manual\_review\_status | 人工审核状态 |
| manual\_comment | 当前审核意见 |
| reviewed\_at | 最近一次人工审核时间 |
| is\_deleted | 是否逻辑删除 |
| deleted\_at | 删除时间 |
| created\_at | 创建时间 |
| updated\_at | 更新时间 |

current\_content 和 original\_content 均采用 JSON 保存。

测试点业务字段包括：

*   requirement\_id
*   category
*   title
*   test\_objective
*   coverage\_description
*   priority
*   source\_rule

未来可以根据测试用例生成需要继续扩展业务字段，而不必频繁修改数据库表结构。

#### 测试点编号规则

采用批次内唯一编号。

例如：

| 批次 | 测试点编号 |
| --- | --- |
| #001 | TP001 |
| #001 | TP002 |
| #001 | TP003 |
| #002 | TP001 |
| #002 | TP002 |

数据库约束：

UNIQUE(batch\_id, point\_id)

不同批次允许出现相同 point\_id。

数据库内部通过 UUID 作为真正的唯一标识，历史记录通过 UUID 关联测试点。

#### AI 原始内容与人工当前内容

original\_content：

*   保存 AI 初次生成的结果。
*   永久保留。
*   人工编辑不得覆盖。

current\_content：

*   保存当前实际使用的测试点内容。
*   人工编辑后更新。
*   审核和 Excel 导出均以当前内容为准。

#### 测试点人工编辑规则

所有测试点业务字段均允许人工修改。

允许编辑：

*   测试点标题
*   需求规则关联
*   测试类型
*   测试目标
*   覆盖描述
*   优先级
*   来源规则

不允许修改：

*   id
*   batch\_id
*   point\_id

修改 requirement\_id 和 source\_rule 时，需要校验对应需求规则是否存在。

编辑后：

1.  更新 current\_content。
2.  original\_content 保持不变。
3.  manual\_review\_status 自动恢复为 pending。
4.  清空当前 manual\_comment。
5.  更新 updated\_at。
6.  写入 edited 操作历史。
7.  原有审核记录继续保留。

#### AI 审查与人工审核状态

两套状态独立管理。

AI 审查状态记录 AI Reviewer 的判断结果。

人工审核状态包括：

*   pending：待审核
*   approved：已通过
*   rejected：已驳回

新生成测试点默认 pending。

AI 审查通过不等于人工审核通过。

#### 人工审核规则

审核通过：

*   状态变为 approved。
*   保存审核时间。
*   保存审核意见。
*   写入 approved 历史记录。

审核驳回：

*   状态变为 rejected。
*   必须填写驳回原因。
*   保存审核时间和驳回原因。
*   写入 rejected 历史记录。
*   不自动重新生成测试点。

驳回后允许继续编辑，编辑后自动恢复 pending，重新进入审核流程。

已通过的测试点也允许再次编辑，编辑后同样恢复 pending。

### 3.6 test\_point\_history — 测试点操作历史表

用途：永久记录测试点的重要操作。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 历史记录唯一 ID |
| test\_point\_id | 测试点内部 UUID |
| batch\_id | 所属生成批次 |
| action\_type | 操作类型 |
| before\_data | 操作前数据 |
| after\_data | 操作后数据 |
| comment | 操作意见或原因 |
| created\_at | 操作时间 |

action\_type 包括：

| 操作类型 | 说明 |
| --- | --- |
| created | 测试点创建 |
| edited | 人工编辑 |
| approved | 审核通过 |
| rejected | 审核驳回 |
| deleted | 逻辑删除 |
| restored | 恢复 |
| batch\_approved | 批量审核通过 |
| batch\_rejected | 批量审核驳回 |

规则：

1.  历史记录不允许编辑或删除。
2.  记录操作前后的完整数据。
3.  单条测试点详情展示独立操作时间线。
4.  批次详情提供批次级操作日志。
5.  批次级日志直接通过 batch\_id 查询，不新增第七张表。
6.  批量审核时，每条测试点分别生成自己的历史记录。
7.  当前版本为个人本地使用，暂不设置 operator\_id。

## 四、数据库关联关系

核心关系：

*   一个项目拥有多份策划文档。
*   同一份策划文档拥有多个版本。
*   一个文档版本可以产生多条需求分析记录。
*   一个需求分析可以产生多个生成批次。
*   一个生成批次拥有多个测试点。
*   一个测试点拥有多条操作历史。

关系示意：

projects  
├── documents  
│ └── 文档版本  
│ └── requirement\_analyses  
│ └── generation\_batches  
│ └── test\_points  
│ └── test\_point\_history

所有关联关系均以内部 ID 为依据，不使用业务编号代替数据库主键。

## 五、删除与归档规则

| 数据对象 | 操作方式 | 是否可恢复 |
| --- | --- | --- |
| 游戏项目 | 归档 | 是 |
| 策划文档 | 逻辑删除 | 是 |
| 需求分析 | 被引用时禁止删除 | 不适用 |
| 生成批次 | 永久保留 | 不适用 |
| 测试点 | 逻辑删除 | 是 |
| 操作历史 | 永久保留 | 不适用 |

测试点逻辑删除：

*   设置 is\_deleted = True。
*   保存 deleted\_at。
*   默认列表不显示已删除测试点。
*   支持恢复。
*   删除后保留原审核状态和内容。
*   恢复后恢复原有内容和审核状态。
*   删除和恢复均记录操作历史。

项目归档：

*   不执行物理删除。
*   归档项目仍可查看历史数据。
*   禁止创建新的需求分析和生成批次。
*   支持恢复为 active。

## 六、人工审核与批量审核

### 6.1 单条审核

支持：

*   单条审核通过。
*   单条审核驳回。
*   修改测试点。
*   查看操作历史。

### 6.2 批量审核

只有 pending 状态的测试点可以参与批量审核。

规则：

1.  只有 pending 测试点显示选择框。
2.  approved 和 rejected 不显示选择框。
3.  批量操作前显示选中数量。
4.  执行前必须二次确认。
5.  批量通过后，选中项分别变为 approved。
6.  批量驳回必须填写驳回原因。
7.  每条记录独立保存审核时间和审核意见。
8.  每条记录分别写入操作历史。

### 6.3 事务要求

以下重要操作必须在同一个 SQLite 数据库事务中完成：

*   更新测试点状态。
*   更新测试点当前内容。
*   插入对应操作历史。

确保状态更新和历史记录写入同时成功或同时回滚。

## 七、生成批次管理与展示

项目主页展示该项目的历史生成批次。

每个批次显示：

*   批次编号
*   生成时间
*   关联需求分析
*   关联策划文档版本
*   测试点总数
*   AI Validator 结果
*   AI Reviewer 结果
*   人工审核进度

进入批次后展示该批次全部有效测试点。

不同批次的测试点不自动合并。

### 人工审核进度统计

只统计未逻辑删除的测试点。

统计三种状态：

*   pending：待审核
*   approved：已通过
*   rejected：已驳回

例如：

总数 20 条：

*   待审核 8 条
*   已通过 10 条
*   已驳回 2 条

人工审核通过率 = approved 数量 / 有效测试点总数 × 100%。

AI 审查状态单独展示，不混入人工审核进度。

## 八、Excel 导出规则

采用按生成批次导出。

支持：

1.  导出当前批次全部有效测试点。
2.  仅导出当前批次人工审核通过的测试点。

规则：

*   不跨批次合并。
*   默认排除逻辑删除的测试点。
*   导出使用 current\_content。
*   保留测试点编号。
*   保留需求关联和来源规则。
*   保留测试目标、覆盖描述、优先级和测试类型。
*   保留前置条件、测试步骤、预期结果等用例字段。
*   保留批次编号及需求分析版本信息。

跨批次合并导出暂不纳入 V0.1，后续版本再考虑。

## 九、数据库备份与恢复

### 9.1 自动备份

采用自动备份 + 手动备份方案。

自动备份规则：

*   重要数据变更前自动备份。
*   自动备份最多保留最近 10 份。
*   超出数量后清理最早的自动备份。
*   备份文件独立存放。
*   使用 SQLite 官方备份机制。

重要数据变更包括：

*   新增需求分析。
*   创建生成批次。
*   新增测试点。
*   编辑测试点。
*   审核通过或驳回。
*   删除和恢复。
*   项目归档及恢复。
*   策划文档版本更新。

### 9.2 手动备份

提供立即备份功能。

*   用户可以随时创建备份。
*   手动备份独立于自动备份保留数量。
*   显示备份时间和文件大小。

### 9.3 数据恢复

恢复流程：

1.  选择需要恢复的备份文件。
2.  展示备份时间和文件大小。
3.  用户二次确认。
4.  自动备份当前数据库。
5.  执行恢复。
6.  检查数据库完整性。
7.  恢复失败时保留原数据库。

恢复过程必须避免直接覆盖唯一可用的数据库文件。

### 9.4 恢复安全要求

建议采用临时数据库文件：

*   先将备份恢复到临时文件。
*   执行 SQLite 完整性检查。
*   检查通过后再替换正式数据库。
*   替换失败时保留当前数据库。
*   保留恢复前自动备份。
